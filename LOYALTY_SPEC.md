# M POS — Программа лояльности

Отдельная спецификация по прямому запросу пользователя. Реализация, замечания и приёмка лояльности ведутся здесь; MASTER описывает подтверждённые возможности, DELTA ссылается на этот документ.

## Текущее состояние и границы

POS: поиск/привязка клиента, прогресс и подарки, скидка отдельной строкой, pending начисления и возвраты, retry, отдельный административный раздел программ/клиентов. Backend: customers, loyalty_programs, earning/reward products, ledger; atomic sale RPC. Telegram: связь клиента и уведомления. Локальная продажа доступна без сети; использование подарка требует подтверждения сервера.

Удаление готовых web-заказов старше суток сохраняется по решению пользователя. Центральная история orders не является полной историей чеков iPad.

## Этапы завершения

1. **Редактор программы (в работе).** Условия отдельным блоком, два каталога с поиском по имени/категории, счётчики выбранного, доступные касанием строки, адаптация узкого экрана и закреплённые действия. Сохранить существующие ID товаров, в том числе отсутствующие локально. Валидировать название и положительные целые количества; блокировать повторное сохранение; при ошибке оставлять заполненную форму. Не включать выключенную программу при редактировании.
2. **Надёжное сохранение backend (обязательно).** Текущий PUT обновляет программу, удаляет и вставляет связи отдельными запросами. Перевести на атомарную транзакцию/RPC с rollback и тестом отказа между этапами; сохранить контракты клиентов. Проверить авторизацию всех изменяющих endpoints, а не только manual adjustment.
3. **Правила подарков.** Решение пользователя: прогресс начисляется только за оплаченные единицы, подарочные исключаются. Серверный расчёт ещё требует изменения и теста смешанного чека (один SKU: платные + подарочные единицы); проверить пересечение программ на одном товаре, скидки и несколько подарков в чеке. Проверить изменение порога при уже накопленном прогрессе. Не менять правила без решения пользователя.
4. **Надёжность оплаты.** Проверить гонку между подтверждением доступности подарка и завершением оплаты, повторные/параллельные запросы, частичный успех нескольких программ, offline pending и возврат до завершения pending начисления. Текущее наличие отдельных тестов не означает завершения полной E2E-проверки.
5. **Клиенты и аналитика.** Явно разделить временные серверные заказы и долговременные локальные чеки. Проверить карточку клиента, корректировку, ограничения доступа и ошибки загрузки. Не обещать полную историю покупок по orders после суточной очистки.
6. **Приёмка iPad.** Создать/изменить программу, поиск и выбор товаров, отмена, отключённая программа, потеря сети при сохранении; продажа/подарок/возврат/retry; ошибка backend не блокирует обычную оплату. После этого обновить статус каждого этапа с фактическими результатами.

Статус: полностью завершённой программа пока не считается; пункты 2–6 открыты.

## D14 — Клиенты и программа лояльности

**Статус:** 🟡 IMPLEMENTED — P1–P7 code complete, ожидается ручная iPad acceptance
**Дата утверждения:** 2026-10-01

### 1. Цель и границы

Создать единую клиентскую базу для POS, WEB и Telegram и на её основе настраиваемую программу лояльности вида «купи N участвующих товаров → получи M подарков». Первая бизнес-конфигурация: кофе 5 → 1 подарок и пицца 7 → 1 подарок, но значения и состав товаров не зашиваются в код.

Центральный backend/DB — источник истины клиентской базы и лояльности. POS остаётся способен проводить обычные продажи при недоступном backend, но не должен небезопасно списывать неизвестную/неподтверждённую награду offline.

### 2. Идентификация клиента

- Основной уникальный идентификатор клиента — нормализованный номер телефона.
- Клиент содержит: id, имя, телефон, optional Telegram user id/username, created/updated timestamps, last purchase timestamp.
- Telegram не обязателен для участия в программе.
- WEB: после подтверждения телефона через Telegram backend находит клиента по телефону или создаёт нового и привязывает Telegram.
- POS: привязка клиента к чеку опциональна. Сотрудник может найти клиента по телефону/последним цифрам или создать нового.
- Обычная продажа без клиента должна продолжать работать штатно.

### 3. Настраиваемые программы

Администратор может создать/включить/выключить программу:
- название;
- requiredQuantity (сколько нужно купить);
- rewardQuantity (сколько наград выдать);
- отдельный набор товаров, начисляющих прогресс;
- отдельный набор товаров, разрешённых как подарок.

Пример: «Кофе»: required=5, reward=1. «Пицца»: required=7, reward=1.

### 4. Начисление

- Прогресс начисляется только после фактического успешного завершения/оплаты чека.
- Корзина, отложенный чек, созданный WEB-заказ и заказ до оплаты ничего не начисляют.
- Количество учитывается: несколько участвующих единиц в одном чеке дают соответствующее количество прогресса.
- Один завершённый чек не может быть начислен повторно: операция должна быть idempotent.
- При пересечении порога создаётся награда, а остаток прогресса переносится дальше.
- Награды могут накапливаться и не сгорают автоматически в v1.

Пример: было 4/5, куплено 3 кофе → выдана 1 награда, новый прогресс 2/5.

### 5. Использование награды

- POS показывает доступные награды выбранного клиента.
- Награду можно применить только к товару из reward product set соответствующей программы.
- Подарочный товар остаётся товаром чека; его обычная цена не переписывается. В чеке отражается отдельная loyalty-компенсация/скидка до 0 BYN.
- Выбор «использовать подарок» резервирует намерение только в текущем чеке.
- Окончательное REWARD_REDEEMED происходит только при успешном завершении продажи.
- Удаление товара, отмена/закрытие незавершённого чека или отказ от подарка не должны списывать награду.
- При недоступном центральном backend POS не списывает награду вслепую; обычная продажа остаётся доступной.

### 6. Ledger — источник истины

Баланс нельзя хранить только изменяемым счётчиком. Источник истины — append-oriented loyalty ledger.

Минимальные типы:
- EARN;
- REWARD_GRANTED;
- REWARD_REDEEMED;
- REVERSAL;
- MANUAL_ADJUSTMENT.

Каждая запись содержит customer, program, связанный order/check (если применимо), quantity, timestamp и metadata/idempotency reference.

Текущий прогресс/баланс наград может храниться как производная/агрегированная проекция для скорости, но должен быть восстанавливаем из ledger.

### 7. Отмены, возвраты и корректировки

- Исторические ledger-записи не удаляются и не переписываются.
- Отмена/возврат создаёт компенсирующую REVERSAL-операцию.
- Администратор может сделать MANUAL_ADJUSTMENT +/- с обязательной причиной и идентификатором администратора.
- Обычный сотрудник не может вручную менять loyalty balance.
- Необходимо исключить двойной reversal и двойное начисление.

### 8. POS UX

В текущем чеке:
- действие «Добавить клиента»;
- поиск/создание клиента;
- после выбора: имя, маскированный телефон, прогресс программ, доступные подарки;
- при наличии подходящего подарка — явное действие «Использовать подарок»;
- возможность сменить/отвязать клиента до завершения чека.

В Панели администратора:
- раздел «Клиенты»;
- поиск по имени/телефону;
- карточка клиента;
- контакты и Telegram status;
- прогресс и доступные награды;
- история покупок;
- ledger/history;
- ручная корректировка с причиной;
- раздел управления программами и составом earning/reward товаров.

### 9. WEB и Telegram

- WEB-заказ использует уже подтверждаемый номер телефона для поиска/создания клиента.
- Сайт не должен считать сохранённый в браузере телефон достаточной авторизацией для показа персональных loyalty данных.
- Telegram может быть персональным каналом уведомлений после подтверждённой привязки.
- Уведомления: начисление прогресса, получение награды, использование награды; возможность отключить их настройкой.
- Первая версия не требует отдельного клиентского аккаунта на сайте.

### 10. Минимальная схема данных

`customers`: id, name, normalized_phone(unique), telegram_user_id(optional), telegram_username(optional), created_at, updated_at, last_purchase_at.

`loyalty_programs`: id, name, required_quantity, reward_quantity, is_active, created_at, updated_at.

`loyalty_earning_products`: program_id, product_id.

`loyalty_reward_products`: program_id, product_id.

`loyalty_ledger`: id, customer_id, program_id, order_id/check_id(optional where justified), type, quantity, idempotency_key/reference, metadata, created_at.

Exact SQL constraints/indexes/migrations are fixed during P1/P2, but uniqueness and idempotency must be enforced at DB/backend boundary, not only UI.

### 11. Analytics-ready data

Архитектура должна позволять без изменения исторической модели считать: всего/новых/повторных клиентов, средний чек, активность loyalty, выданные/использованные/неиспользованные награды, количество и стоимость подарков, повторные покупки/retention. Эти метрики не обязательны для первого UI релиза, но исходные события должны сохраняться с первой версии.

### 13. Acceptance invariants

1. Один нормализованный телефон не создаёт двух клиентов.
2. Telegram linkage не заменяет подтверждённый телефон как customer identity.
3. Незавершённый/неоплаченный/отменённый до оплаты заказ не начисляет прогресс.
4. Повторная доставка события завершения чека не даёт повторное начисление.
5. N товаров корректно пересекают один или несколько порогов и сохраняют remainder.
6. Награда не исчезает до успешного завершения чека с redemption.
7. Отмена незавершённого чека освобождает выбранную награду.
8. Reward применяется только к разрешённому reward product.
9. Несколько накопленных наград учитываются независимо.
10. Refund/reversal не удаляет историю, а создаёт компенсирующую операцию.
11. Повтор reversal безопасен.
12. Manual adjustment доступен только администратору и требует причины.
13. Offline backend не блокирует обычную POS-продажу.
14. Offline POS не может небезопасно потратить центральную награду.
15. WEB не раскрывает персональный loyalty status только по данным localStorage/browser phone.
16. Ledger позволяет объяснить текущий прогресс и количество наград клиента.
17. Изменение правил программы в будущем не должно переписывать уже совершённые ledger-события.
18. Недоступность интернета/backend не может блокировать наличную или карточную оплату, завершение обычной продажи, локальное сохранение чека и локальные кассовые операции.
19. Offline loyalty accrual сохраняется как pending и синхронизируется после восстановления связи; центральная reward redemption без подтверждения backend не выполняется.

## Исправление привязки web-заказа

Причина: checkout сохранял orders.customer_id, но SSE projection не включал поле; POS также отбрасывал его при создании отложенного чека. Исправлена передача customer_id → parked.customer.id → currentOrderSession.customer.id → paid order.customer.id. При открытии отложенного чека баланс загружается неблокирующе, старые выбранные подарки очищаются. Начисление только после оплаты; при недоступном backend действует существующая pending-очередь. 144 POS-теста и 44 backend-теста пройдены. Исторические принятые чеки без ID автоматически не изменяются; в неоплаченном заказе можно выбрать клиента вручную. Нужен реальный web→Telegram→iPad→оплата acceptance после обновления приложения.


### Дополнительный разрыв нормализации входящего события

Реальная повторная проверка выявила, что normalizeWebOrder отбрасывал customer_id до acceptWebOrder. Предыдущий тест начинал с готового state.webEvents и этот слой не покрывал. Исправлена нормализация и сравнение событий: поступивший customer_id сохраняется даже при том же ID/статусе/сумме заказа. Новый regression проходит через EventSource.onmessage → normalizeWebOrder → локальное сохранение/перезагрузку события → приёмку → открытие → payload начисления. 146/146 Node tests и simulator build успешны. Прочитанные последние production-заказы имеют customer_id и Telegram-подтверждение; данные БД не изменялись. Нужна новая сборка iPad и повторный заказ; ранее принятые записи без ID автоматически не восстанавливаются.
