# M POS — DELTA SPEC

> Единственный список того, что ЕЩЁ НЕ завершено.
>
> После реализации пункт должен быть удалён отсюда и его фактический результат должен быть сразу внесён в `MASTER_SPEC.md`. Выполненные задачи в DELTA не хранятся.

## Правило выполнения задачи

Для каждого пункта:
1. проверить текущее состояние кода перед изменением;
2. реализовать минимально безопасное изменение;
3. проверить UI, бизнес-логику, локальное хранение и связанные печать/сеть/экспорт;
4. не ломать offline-first работу;
5. выполнить автоматические проверки;
6. при необходимости проверить на физическом iPad;
7. только после завершения удалить пункт из DELTA;
8. обновить MASTER и, если это релиз, `CURRENT_VERSION`.

## D1 — Единая техническая точка версии

**Статус: требуется. Приоритет: высокий.**

Сейчас каноническая документальная версия задаётся в `MASTER_SPEC.md`, но Xcode также содержит `MARKETING_VERSION`. Нужно устранить ручное дублирование.

Требование:
- `CURRENT_VERSION` из MASTER должен стать единственным значением, которое разработчик меняет вручную;
- build process должен автоматически применять его к `CFBundleShortVersionString` и подписи версии в UI;
- Debug и Release должны получать одинаковую версию;
- сборка должна завершаться ошибкой при отсутствующем/некорректном `CURRENT_VERSION`;
- не должно требоваться ручное изменение версии одновременно в MASTER, pbxproj, Info.plist и HTML.

Acceptance:
- изменение одной строки `CURRENT_VERSION` меняет системную версию приложения и подпись в Быстрых настройках.

## D2 — Local-first сохранение фотографии товара

**Статус: известный архитектурный долг. Приоритет: высокий.**

Сейчас при новом фото `saveProduct()` выполняет upload на backend до окончательного локального сохранения товара.

Нужно:
- локальное изменение товара не должно зависеть от доступности backend;
- фото должно сохраняться/подготавливаться локально;
- upload должен быть отдельной сетевой операцией;
- ошибка сети не должна отменять валидные локальные изменения;
- не допустить перезаписи более нового товара результатом старого upload;
- определить локальное pending-состояние фото без автоматической фоновой отправки.

Acceptance:
- товар с изменениями можно сохранить без интернета;
- после перезапуска локальные изменения не теряются;
- отправка наружу происходит только по согласованному сетевому действию.

## D3 — Уточнить и изолировать входящие web-заказы относительно manual-only sync

**Статус: частичное архитектурное расхождение. Приоритет: высокий.**

`loadAll()` автоматически запускает `startWebOrderEvents()` и EventSource. Это нужно для входящих web-заказов, но общий контракт manual-only запрещает автоматическую исходящую синхронизацию.

Нужно:
- формально разделить два понятия в коде: входящий канал web-заказов и исходящая синхронизация POS;
- гарантировать, что EventSource не публикует локальные POS-данные и не перезаписывает авторитетное локальное состояние;
- проверить reconnect/error lifecycle;
- сделать невозможным случайное использование входящего канала как скрытого sync trigger;
- покрыть это тестами.

Acceptance:
- ручная кнопка остаётся единственным стандартным триггером POS → backend;
- EventSource обслуживает только входящие события заказов;
- offline POS не зависит от EventSource.

## D4 — Завершить постепенное разделение pos.html на модули

**Статус: частично реализовано. Приоритет: средний.**

Основной runtime и большая часть бизнес-логики всё ещё находятся в `pos.html`. В `Web` существуют подготовленные границы, часть которых не является активными runtime-модулями.

Целевое направление:
```
Web UI
 → business modules
 → local storage
 → explicit/manual sync
```

Миграция только по одному домену за этап:
- products/categories;
- sales/cart/checkout;
- receipts/returns;
- shifts/cash movements;
- suppliers/purchase orders/receiving;
- analytics;
- settings.

Нельзя делать полный rewrite `pos.html` одним изменением.

Acceptance каждого этапа:
- поведение до/после совпадает;
- ключи/JSON совместимы;
- offline работает;
- тесты проходят;
- физический iPad проверен перед следующим крупным этапом.

## D5 — Удалить остатки Bluetooth-конфигурации

**Статус: технический долг. Приоритет: средний.**

Печать уже LAN-only, но:
- файл называется `BluetoothPrinterManager.swift`;
- Xcode references используют старое имя;
- `Info.plist` содержит `NSBluetoothAlwaysUsageDescription`.

Нужно:
- переименовать manager в сетевое имя;
- безопасно обновить Xcode file references/build sources;
- удалить Bluetooth permission, если ни одна другая функция приложения реально его не использует;
- проверить LAN print test, оплату, kitchen ticket и reprint.

Acceptance:
- в runtime/configuration нет Bluetooth-зависимости;
- LAN TCP/9100 печать полностью работает.

## D6 — Полноценный неизменяемый журнал складских движений

**Статус: не реализовано. Приоритет: средний.**

Текущий складской отчёт реконструирует часть истории из текущего остатка, приёмок и `stockConsumption`. Ручные исторические изменения склада не образуют полного ledger.

Нужно отдельно спроектировать:
- immutable stock movement;
- тип движения;
- productId;
- quantity;
- unit;
- unit cost/cost snapshot;
- source document/id;
- timestamp;
- employee/reason для ручной корректировки;
- возвраты;
- миграционную стратегию без выдумывания старой истории.

До реализации текущий складской отчёт остаётся аналитическим, а не юридически значимым бухгалтерским регистром.

## D7 — Локальный OCR документов приёмки

**Статус: planned / не реализовано. Приоритет: будущая функция.**

Цель: фото документа → локальный Apple Vision OCR → parser → локальное сопоставление каталога → редактируемый draft → явное подтверждение приёмки.

Обязательные ограничения:
- iPad 10 / A14 должен поддерживаться;
- Apple Intelligence не является зависимостью;
- OCR работает без интернета;
- фото/распознанный текст не отправляются в Railway/Supabase/OpenAI;
- OCR никогда автоматически не проводит склад;
- ошибка OCR оставляет доступной обычную ручную приёмку;
- неоднозначные позиции требуют подтверждения;
- в будущем допускается локальная память supplier aliases.

Этапы: proof of concept → parser → catalog matching → supplier mapping → production integration.

## D8 — Telegram-подтверждение телефона для web-заказов

**Статус: planned / не реализовано в POS-проекте. Приоритет: будущая функция.**

Это backend/web security feature и не должно влиять на локальные продажи POS.

Требуется:
- одноразовая verification session;
- криптографически случайный короткоживущий token;
- Telegram deep link;
- `request_contact`;
- проверка, что контакт принадлежит отправителю;
- server-side нормализация и сравнение телефона;
- single-use/expiry/consume;
- order endpoint самостоятельно требует валидную verification;
- rate limits и anti-abuse;
- секреты только на backend;
- корзина не теряется при переходе в Telegram;
- в будущем возможен signed trusted-device credential.

Нельзя считать подтверждением:
- просто введённый телефон;
- frontend/localStorage flag;
- произвольный текст номера в Telegram;
- URL-параметр без server-side verification.

Нужно провести регрессионный physical-iPad smoke test текущего main:

## D10 — Проверить атомарность критических многоключевых операций

**Статус: ограничение текущей реализации. Приоритет: средний.**

Проведение приёмки и некоторые другие операции сохраняют несколько local-storage ключей последовательно. Это не ACID-транзакция.

Нужно:
- перечислить все операции, где одно бизнес-действие меняет несколько ключей;
- определить поведение при storage failure между записями;
- добавить recovery/journal там, где частичное сохранение может нарушить деньги, остатки или документы;
- сохранить совместимость текущих данных.

Приоритет проверки: оплата/чек/смена → возврат → приёмка → закупка.

## D11 — Очистить legacy/неподключённые storage/sync слои

**Статус: технический долг. Приоритет: после стабилизации модульной миграции.**

В `Web/js` существуют старые/подготовительные storage и sync-файлы с разными контрактами.

Нужно:
- определить единственный runtime storage adapter;
- удалить или мигрировать неиспользуемые альтернативы;
- не подключать новый sync layer автоматически;
- сохранить manual-only POS → backend;
- убедиться, что bundle не содержит вводящих в заблуждение альтернативных реализаций.

## D12 — Регрессионная автоматизация печати и native bridge

**Статус: частично покрыто. Приоритет: средний.**

Добавить воспроизводимые проверки контрактов:
- printer payload;
- routing payment/kitchen;
- copies;
- category routing;
- comments toggle;
- register label;
- random footer phrase;

Native raster/layout всё равно требует визуальной проверки на реальном принтере.
