# M POS — DELTA SPEC

> Единственный список того, что ЕЩЁ НЕ завершено.
>
> После реализации пункт должен быть удалён отсюда и его фактический результат должен быть сразу внесён в `MASTER_SPEC.md`. Выполненные задачи в DELTA не хранятся.

## Правило выполнения задачи

Для каждого пункта:
1. проверить текущее состояние кода перед изменением;
2. реализовать минимально безопасное изменение;
3. проверить UI, бизнес-логику, локальное хранение и связанные печать/сеть/экспорт;
4. не ломать offline-first работу;
5. выполнить автоматические проверки;
6. при необходимости проверить на физическом iPad;
7. только после завершения удалить пункт из DELTA;
8. обновить MASTER и, если это релиз, `CURRENT_VERSION`.

## D1 — Единая техническая точка версии

**Статус: требуется. Приоритет: высокий.**

Сейчас каноническая документальная версия задаётся в `MASTER_SPEC.md`, но Xcode также содержит `MARKETING_VERSION`. Нужно устранить ручное дублирование.

Требование:
- `CURRENT_VERSION` из MASTER должен стать единственным значением, которое разработчик меняет вручную;
- build process должен автоматически применять его к `CFBundleShortVersionString` и подписи версии в UI;
- Debug и Release должны получать одинаковую версию;
- сборка должна завершаться ошибкой при отсутствующем/некорректном `CURRENT_VERSION`;
- не должно требоваться ручное изменение версии одновременно в MASTER, pbxproj, Info.plist и HTML.

Acceptance:
- изменение одной строки `CURRENT_VERSION` меняет системную версию приложения и подпись в Быстрых настройках.

## D2 — Local-first сохранение фотографии товара

**Статус: известный архитектурный долг. Приоритет: высокий.**

Сейчас при новом фото `saveProduct()` выполняет upload на backend до окончательного локального сохранения товара.

Нужно:
- локальное изменение товара не должно зависеть от доступности backend;
- фото должно сохраняться/подготавливаться локально;
- upload должен быть отдельной сетевой операцией;
- ошибка сети не должна отменять валидные локальные изменения;
- не допустить перезаписи более нового товара результатом старого upload;
- определить локальное pending-состояние фото без автоматической фоновой отправки.

Acceptance:
- товар с изменениями можно сохранить без интернета;
- после перезапуска локальные изменения не теряются;
- отправка наружу происходит только по согласованному сетевому действию.

## D3 — Уточнить и изолировать входящие web-заказы относительно manual-only sync

**Статус: частичное архитектурное расхождение. Приоритет: высокий.**

`loadAll()` автоматически запускает `startWebOrderEvents()` и EventSource. Это нужно для входящих web-заказов, но общий контракт manual-only запрещает автоматическую исходящую синхронизацию.

Нужно:
- формально разделить два понятия в коде: входящий канал web-заказов и исходящая синхронизация POS;
- гарантировать, что EventSource не публикует локальные POS-данные и не перезаписывает авторитетное локальное состояние;
- проверить reconnect/error lifecycle;
- сделать невозможным случайное использование входящего канала как скрытого sync trigger;
- покрыть это тестами.

Acceptance:
- ручная кнопка остаётся единственным стандартным триггером POS → backend;
- EventSource обслуживает только входящие события заказов;
- offline POS не зависит от EventSource.

## D4 — Завершить постепенное разделение pos.html на модули

**Статус: частично реализовано. Приоритет: средний.**

Основной runtime и большая часть бизнес-логики всё ещё находятся в `pos.html`. В `Web` существуют подготовленные границы, часть которых не является активными runtime-модулями.

Целевое направление:
```
Web UI
 → business modules
 → local storage
 → explicit/manual sync
```

Миграция только по одному домену за этап:
- products/categories;
- sales/cart/checkout;
- receipts/returns;
- shifts/cash movements;
- suppliers/purchase orders/receiving;
- analytics;
- settings.

Нельзя делать полный rewrite `pos.html` одним изменением.

Acceptance каждого этапа:
- поведение до/после совпадает;
- ключи/JSON совместимы;
- offline работает;
- тесты проходят;
- физический iPad проверен перед следующим крупным этапом.

## D13 — Динамический ETA web-заказов и планирование загрузки производственных станций

**Статус: planned / архитектура согласована, не реализовано. Приоритет: будущая функция после стабилизации web-order канала.**

### Цель

Web-клиент должен получать реалистичное **ориентировочное время готовности заказа**, учитывающее состав конкретной корзины, текущую фактическую загрузку заведения, разные производственные станции, активные локальные и web-заказы, предварительные заказы на будущее время, параллельное приготовление и временную потерю связи между iPad и backend.

Нельзя рассчитывать ETA только по количеству отложенных чеков, количеству заказов или одной общей очереди. Большой и маленький заказ создают разную нагрузку, бар и кухня работают параллельно, а заказ на 18:00 не должен загружать расчёт для клиента в 13:00.

ETA является **оценкой**, а не гарантированным временем. Клиенту предпочтительно показывать диапазон, например «25–35 минут», а не ложную точность «27 минут».

### 1. Производственные станции

Ввести отдельную сущность/справочник PreparationStation, а не жёсткие boolean-поля kitchen/bar.

Начальные станции:
- Кухня;
- Бар;
- Без приготовления.

Архитектура должна позволять позднее добавить без переделки модели Пиццу, Выпечку, Холодный цех и другие станции.

Товар должен иметь производственную конфигурацию, достаточную для оценки его вклада в нагрузку: stationId, базовую оценку времени приготовления и/или нормализованную единицу нагрузки, признак отсутствия приготовления.

Конкретная формула и единицы должны быть откалиброваны отдельно. Не считать минуты всех позиций простым последовательным сложением: несколько товаров могут готовиться параллельно.

### 2. Модификаторы

Модификаторы товара также участвуют в производственной нагрузке, если связанный товар требует приготовления. Например, добавление бекона может увеличить нагрузку кухни, сироп — бара, а модификатор без приготовления может не добавлять нагрузку.

Расчёт должен использовать фактически выбранные модификаторы конкретной строки заказа, а не только текущую конфигурацию базового товара.

### 3. Разделение заказа по станциям

Один заказ может одновременно создавать нагрузку на несколько станций: пицца и драники → Кухня, капучино → Бар.

Backend/POS должны уметь получить для заказа отдельные station workloads. Станции работают параллельно. Ориентировочная готовность всего заказа определяется временем, когда завершится наиболее поздняя необходимая часть заказа, а не суммой времени Бар + Кухня.

### 4. ASAP и заказ ко времени

У web-заказа должен быть явно определён режим исполнения:
- ASAP — как можно скорее;
- SCHEDULED — к выбранному времени.

Для scheduled-заказа хранить requestedTime или эквивалентное поле.

Заказ, оформленный в 13:00 на 18:00, сохраняется и виден в системе, но не считается текущей нагрузкой кухни в 13:00. Он создаёт прогнозируемую нагрузку в соответствующем временном окне перед 18:00 и учитывается при оценке других заказов на близкое время.

Наличие заказа в «Отложенных» само по себе не означает текущую производственную нагрузку.

### 5. Временная шкала загрузки

Целевая модель расчёта — нагрузка станции во времени, а не одно глобальное число. Backend должен уметь оценивать Kitchen load и Bar load по временным окнам, нагрузку будущих scheduled-заказов и текущую незавершённую работу.

Размер временного bucket и конкретный scheduling algorithm определить при реализации после тестирования на реальных данных.

Необходимо избежать двойного учёта одного web-заказа одновременно как известного backend заказу и как части агрегата, полученного от POS.

### 6. Источники нагрузки

Backend уже является источником истины для созданных через web заказов и знает их состав и желаемое время. Но backend не знает автоматически обо всей локальной работе POS: заказах, созданных непосредственно на iPad, изменениях статусов, фактическом начале/окончании работы и других локальных событиях, влияющих на загрузку.

Поэтому для ETA требуется отдельный **операционный POS → backend канал**.

Это НЕ стандартная синхронизация каталога и НЕ отменяет правило manual-only для обычной исходящей синхронизации POS.

Должны быть строго разделены:
1. ручная синхронизация каталога/данных POS → backend;
2. входящий backend → POS канал web-заказов;
3. автоматический узкий operational-state канал POS → backend для ETA, статусов и heartbeat.

Operational channel не должен становиться скрытым триггером полной синхронизации POS.

### 7. POS → backend operational state

iPad должен событийно отправлять только необходимое для оперативного состояния при событиях, влияющих на ETA: создан локальный заказ; web-заказ получен POS; заказ принят; начато приготовление; заказ готов; заказ отменён; изменено requested time; локальный заказ завершён или удалён из активной производственной очереди.

Предпочтительно не передавать web-клиенту и не публиковать лишние данные чеков, сотрудников, денег и локальной БД.

Допускается агрегированный snapshot: нагрузка по stationId, количество активных работ, временные buckets будущей нагрузки, updatedAt, идентификатор POS/device/location, если в будущем появится несколько точек.

Точный API-контракт определить при реализации.

### 8. Heartbeat и свежесть данных

POS должен периодически отправлять лёгкий heartbeat независимо от событий изменения очереди.

Backend хранит как минимум lastPosHeartbeatAt, время последнего operational snapshot и состояние свежести snapshot. Нельзя бесконечно считать старый snapshot текущей реальной загрузкой.

Пороговые значения должны быть конфигурируемыми. Начальные значения 5/20 минут могут использоваться только как стартовая гипотеза и должны быть подтверждены эксплуатацией.

### 9. Поведение при потере интернета / недоступном iPad

Потеря связи с iPad не должна автоматически уничтожать или терять web-заказы.

Предусмотреть три состояния.

**ONLINE**
- heartbeat/snapshot свежий;
- backend рассчитывает динамический ETA с фактической нагрузкой;
- клиент получает обычный диапазон ETA.

**STALE / кратковременная потеря связи**
- POS недавно перестал отвечать;
- web-заказ всё ещё можно принять;
- старую загрузку нельзя выдавать за актуальную;
- использовать безопасный fallback: базовое время корзины + консервативный запас/расширенный диапазон;
- клиенту не показывать технические сообщения «iPad offline», «POS недоступен»;
- пользовательское сообщение должно быть бизнесовым, например: «Ориентировочно 30–50 минут. Точное время приготовления уточним после подтверждения заказа».

**OFFLINE / длительная потеря связи**
- если POS не отвечает дольше настроенного безопасного порога, новые web-заказы временно блокируются, чтобы заведение не накапливало заказы, о которых персонал не знает;
- клиенту показывать нейтральное сообщение вроде «Онлайн-заказы временно недоступны. Попробуйте немного позже»;
- уже созданные заказы не теряются.

Переходы ONLINE → STALE → OFFLINE и обратно определяются backend по heartbeat, а не frontend.

### 10. Backend как надёжное хранилище web-заказов

Факт принятия web-заказа не должен зависеть от мгновенной доступности iPad. Сначала backend атомарно сохраняет валидный заказ, затем доставляет его POS.

Для доставки предусмотреть серверные состояния или эквивалент:
- заказ сохранён;
- awaiting_pos_delivery;
- доставлен в POS;
- POS подтвердил получение;
- дальнейшие business statuses заказа.

Нельзя считать отправку события успешной доставкой без подтверждения POS.

После восстановления связи POS должен получить **все** недоставленные ему заказы в правильном состоянии, а не только последнее событие.

Повторная доставка должна быть идемпотентной: reconnect/retry не должен создавать дубликаты чеков.

### 11. Web UX

До оформления и/или в корзине web может запрашивать ETA для текущего состава корзины.

Ответ клиенту предпочтительно давать диапазоном: «15–25 минут», «25–35 минут» и т.п.

Не раскрывать пользователю внутренние load units, состояние iPad, heartbeat и техническую топологию.

Для scheduled-заказа backend должен учитывать нагрузку выбранного временного окна. В будущем при перегруженном окне допускается показать расширенный диапазон, предложить ближайшее доступное время или запретить недостижимый slot.

Это должно быть серверным решением, а не расчётом только во frontend.

### 12. Расчёт ETA v1

Первую production-версию делать детерминированной и объяснимой, без ML/AI.

Она должна учитывать:
1. базовую производственную характеристику товаров и выбранных модификаторов;
2. разбиение по станциям;
3. текущую активную нагрузку каждой станции;
4. scheduled load соответствующего временного окна;
5. параллельность станций;
6. безопасный диапазон/буфер.

Итоговый ETA заказа определяется по самой поздней необходимой станции.

Не использовать только activeOrdersCount как ETA: три простых заказа могут быть легче одного большого.

### 13. Будущая адаптация по фактической истории

Архитектура должна позволять позже собирать фактические timestamps: заказ создан/принят, начал готовиться, готов, выдан/закрыт при необходимости.

После накопления достаточной статистики можно корректировать базовые оценки по фактической работе конкретного заведения: по товару, станции, размеру заказа, уровню загрузки, времени суток или дню недели — только если данные действительно покажут пользу.

Это будущий этап. Первая версия не должна зависеть от ML и не должна автоматически менять нормативы без прозрачной логики.

### 14. Offline-first POS

Новая функция не должна ухудшить главное правило M POS: локальная касса продолжает работать без интернета.

При отсутствии backend:
- локальный заказ создаётся;
- оплата, чек и склад продолжают работать;
- operational updates могут быть поставлены в ограниченную очередь/retry-механизм;
- восстановление сети не должно блокировать UI;
- сетевые ошибки ETA не должны влиять на локальные денежные операции.

Нужна защита от бесконечного роста очереди технических snapshots: snapshot может заменять предыдущий, а события доставки web-заказов/подтверждений должны иметь отдельную надёжную семантику.

### 15. Безопасность и минимизация данных

Operational endpoint должен быть аутентифицирован, принимать данные только от зарегистрированного POS/location, валидировать timestamps и payload, не доверять frontend значениям загрузки, не раскрывать клиенту внутренние данные POS и иметь rate limit/replay/idempotency protection по необходимости.

Web ETA endpoint возвращает только необходимый клиенту результат и публичное состояние возможности заказа.

### 16. Наблюдаемость

Для диагностики без доступа к локальной БД нужны server-side технические метрики/логи:
- последний heartbeat;
- последний snapshot;
- ONLINE/STALE/OFFLINE;
- число ожидающих доставки web-заказов;
- возраст самого старого недоставленного заказа;
- ошибки доставки/reconnect;
- версия ETA algorithm/config.

Не логировать лишние персональные или платёжные данные.

### 17. Предлагаемые этапы реализации

**Этап A — модель:** PreparationStation; station assignment товара; базовые preparation/load параметры; ASAP/SCHEDULED + requestedTime; modifier contribution.

**Этап B — operational channel:** heartbeat; authenticated POS → backend endpoint; snapshot/event contract; freshness states.

**Этап C — надёжная доставка web-заказов:** persistent delivery state; POS acknowledgement; retry/reconnect; idempotency; recovery всех missed orders.

**Этап D — ETA v1:** station workloads; temporal buckets; current + scheduled load; deterministic range calculation; fallback при stale POS.

**Этап E — Web UX:** ETA в корзине; ETA перед подтверждением; scheduled slots; понятные ONLINE/STALE/OFFLINE business messages без технических деталей.

**Этап F — статистическая калибровка:** фактические timestamps; отчёт predicted vs actual; ручная/контролируемая настройка коэффициентов; только затем рассматривать автоматическую адаптацию.

### 18. Acceptance criteria

Функция считается завершённой только если подтверждены сценарии:
- маленький и большой заказ дают различную нагрузку;
- Бар и Кухня рассчитываются независимо и параллельно;
- mixed order готов по наиболее поздней станции;
- заказ на 18:00 не увеличивает текущую нагрузку в 13:00, но влияет на своё будущее окно;
- локальные POS-заказы влияют на web ETA после operational update;
- выбранные модификаторы корректно влияют на соответствующую станцию;
- web-заказ сохраняется backend до попытки доставки POS;
- краткий offline iPad не теряет заказ и даёт клиенту fallback ETA;
- длительный offline переводит web в безопасное временное прекращение новых заказов;
- reconnect доставляет все пропущенные заказы ровно один раз логически;
- старый snapshot не используется как актуальная загрузка;
- manual catalog sync остаётся manual-only;
- локальная POS касса полностью работает без backend;
- расчёт ETA покрыт unit/integration тестами;
- reconnect/idempotency/offline сценарии покрыты тестами;
- финальный сценарий проверен на физическом iPad и web-клиенте.
