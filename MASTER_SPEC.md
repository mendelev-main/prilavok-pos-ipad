# M POS — MASTER SPEC

> Единственный источник правды о том, что УЖЕ реализовано в приложении.
>
> В репозитории разрешены только два Markdown-файла: `MASTER_SPEC.md` и `DELTA_SPEC.md`.
> Всё, что ещё не реализовано или требует исправления, хранится только в `DELTA_SPEC.md`.

## 0. Версия и обязательный процесс

**CURRENT_VERSION: 130.51**

**APP_NAME: M POS**

Публичное название приложения и бренда POS: **M POS**. Исторические технические идентификаторы (`PrilavokPOS`, bundle identifier, `prilavok_` storage prefix и имена файлов) сохраняются для совместимости и не считаются пользовательским названием.

`CURRENT_VERSION` в этом файле — каноническая версия проекта и единственная документальная точка версионирования.

Правила работы:
1. MASTER описывает только фактически реализованное состояние текущего `main`.
2. DELTA описывает только то, что ещё требуется реализовать, исправить, проверить или мигрировать.
3. Новая задача сначала добавляется/уточняется в DELTA.
4. После реализации задачи код и проверки завершаются до изменения статуса документации.
5. Сразу после успешной реализации пункт удаляется из DELTA, а фактическое новое состояние переносится в соответствующий раздел MASTER.
6. Если изменение повышает версию, сначала меняется `CURRENT_VERSION` здесь; техническая версия сборки должна соответствовать ему.
7. Нельзя оставлять выполненную задачу в DELTA и нельзя описывать в MASTER будущий функционал как существующий.
8. Существенные изменения проверяются на физическом iPad. Если проверка ещё не выполнена, это остаётся пунктом DELTA.
9. POS нельзя ломать ради рефакторинга. Приоритет: касса → локальные данные → печать → безопасная синхронизация → новые функции.
10. Commit/push выполняются только в рамках явно согласованной пользователем работы.

## 1. Назначение и архитектура

M POS — локальное iPad POS-приложение для кафе.

Фактическая схема:
```
iPad app (Swift/UIKit)
        ↓
WKWebView
        ↓
PrilavokPOS/pos.html
        ├─ UI и основная бизнес-логика
        ├─ локальное состояние
        ├─ core/storage.js через совместимый loadKey/saveKey
        ├─ network-printer.js
        └─ сетевые функции backend/web orders
        ↓
Native bridges in PrilavokPOSApp.swift
        ├─ LAN receipt printing
        ├─ share/PDF/XLSX
        ├─ photo picker / image processing
        ├─ Telegram-related bridge
        └─ native notification sound
```

Backend используется через Railway, удалённые данные — через backend/Supabase. Основной runtime интерфейса и значительная часть бизнес-логики всё ещё находятся в `PrilavokPOS/pos.html`.

Каталог `PrilavokPOS/Web` содержит постепенно выделяемые границы модулей. Наличие файла в Web не означает, что он является самостоятельным runtime-модулем. Реальный storage adapter находится в `Web/js/core/storage.js` и подключён совместимо к существующим `loadKey/saveKey`.

## 2. Главные правила данных

- iPad POS — источник истины для операционных данных.
- Основная работа POS должна быть доступна без интернета.
- Локальные данные имеют приоритет над backend/web.
- Локальное сохранение не должно зависеть от успешной синхронизации.
- Стандартная публикация меню выполняется вручную через Настройки → Сетевые настройки → «Синхронизировать меню» → `syncMenuToBackend()`.
- Backend не должен автоматически заменять локальное состояние POS.
- Формат существующих локальных данных нельзя менять без совместимой миграции.
- Используется префикс localStorage `prilavok_`.
- Резервные копии должны сохранять совместимость со старыми данными.

Фактическое исключение: входящие web-заказы используют `EventSource`, запускаемый `startWebOrderEvents()` после загрузки POS. Это входящий канал заказов, а не стандартная публикация локального меню.

## 5. Остатки, рецептуры и возвраты

- Простые товары могут учитывать остаток или работать без его учёта.
- Составные товары содержат компоненты.
- Вложенные рецептуры разворачиваются до простых ингредиентов.
- Перед оплатой проверяется суммарный расход всей корзины.
- Циклы рецептур, отсутствующие ингредиенты и некорректные количества блокируются.
- Новый чек сохраняет `stockConsumption: {version:1, items:[...]}`.
- Snapshot расхода используется для точного возврата даже после последующего изменения рецептуры.
- Товар, необходимый для возврата нового чека, защищён от несовместимого удаления/смены типа.
- Старые чеки без snapshot используют legacy-путь возврата и не переписываются задним числом.

## 14. LAN-печать

Поддерживается только печать на принтеры локальной сети.

Фактический путь:
```
pos.html / network-printer.js
 → WKWebView message handler "printer"
 → PrilavokPOSApp.swift
 → BluetoothPrinterManager.swift (историческое имя)
 → Network.framework / NWConnection
 → TCP/9100
 → ESC/POS
 → Xprinter XP-N160II / совместимый LAN-принтер
```

Bluetooth как транспорт печати не используется.

Реализовано:
- несколько сетевых принтеров;
- независимая маршрутизация платёжных и кухонных чеков;
- выбор категорий для кухонного принтера;
- несколько копий;
- тестовая печать;
- автоматическая печать после оплаты;
- ручная печать/повторная печать;
- кухонный чек при парковке/отложенном заказе согласно маршрутизации;
- фиксированный raster-render платёжного чека под 80 мм;
- отдельный кухонный шаблон;
- комментарии;
- переключатель печати комментария на платёжном чеке;
- настраиваемая подпись кассы;
- случайные нижние фразы;
- настраиваемый заголовок платёжного чека.

Print Bridge, desktop helper, Windows/Mac-драйвер в штатном пути не требуются.

## 15. Backend и web-заказы

- Настройки хранят backend URL, device key/name.
- `syncMenuToBackend()` формирует и отправляет каталог вручную.
- Существует проверка соединения и создание тестового web-заказа.
- Входящие web-заказы принимаются через EventSource.
- Есть локальная обработка/журнал принятия web-заказов.
- Сетевой сбой не должен блокировать обычную локальную продажу.

## 16. Локальное хранение и backup

- Используется совместимый storage adapter.
- Логические ключи сохраняются под префиксом `prilavok_`.
- Основные сущности: products, shifts, employees, orders, parked, receivings, suppliers, purchaseOrders, discounts, layout, printer/settings, company, delivery rates, network, текущий заказ, web events, posNavigation и другие рабочие настройки.
- Экспорт/импорт резервной копии сохраняет основные операционные данные.
- Backup v10 включает локальную навигацию.
- Старые данные читаются совместимо, если для конкретного расширения явно не требуется миграция.

## 17. Native iPad layer

`PrilavokPOSApp.swift`:
- создаёт WKWebView;
- загружает локальный POS;
- обслуживает JS/native message handlers;
- передаёт печать в native printer manager;
- предоставляет native share/export;
- работает с фото;
- поддерживает нативные функции, которые невозможно/нежелательно выполнять только в HTML.

`BluetoothPrinterManager.swift` — историческое имя LAN printer manager; фактическая передача выполняется через `NWConnection`.

- недостаточный остаток;
- циклы;
- возврат по snapshot;
- legacy-чеки;
- платежи;
- единицы;
- поставщиков/заказы/приёмку;

Автоматический тест не заменяет физическую проверку iPad для UI, жестов, печати и native share.

## 19. Правило дальнейшего развития

Любое изменение проекта обязано сохранять этот цикл:

```
DELTA: задача
   ↓
реализация
   ↓
автоматические/синтаксические проверки
   ↓
iPad-проверка, если она нужна
   ↓
удалить выполненный пункт из DELTA
   ↓
обновить фактическое состояние в MASTER
   ↓
при релизе обновить CURRENT_VERSION в MASTER
```

MASTER никогда не является wishlist. DELTA никогда не является историей уже выполненных работ.
