# Prilavok POS — постоянные правила разработки

## Источники и текущая архитектура

- Правила действуют для всего репозитория. Перед работой читать README.md, PROJECT_MEMORY.md, PROJECT_RULES.md и документацию затрагиваемой области в docs и PrilavokPOS/Web.
- Актуальный контракт OFFLINE-FIRST и ручной синхронизации описан в docs/OFFLINE_FIRST_ARCHITECTURE.md. Упоминания фоновой синхронизации в docs/DATA_FLOW_AUDIT.md и docs/DATA_FLOW_AUDIT_PLAN.md исторические: их заменило требование manual-only в v130.13 (коммит d885c3a). Они не разрешают автоматическую синхронизацию.
- Приложение: Swift/UIKit + WKWebView. PrilavokPOS/PrilavokPOSApp.swift загружает локальный pos.html и обеспечивает нативные мосты печати, Telegram и выбора фото. BluetoothPrinterManager.swift отвечает за Bluetooth-принтер и кодирование чека. Backend: Railway; база данных: Supabase.
- PrilavokPOS/pos.html остаётся действующим источником интерфейса, бизнес-логики и хранения. В PrilavokPOS/Web находятся границы будущих модулей; data/* и core/state.js пока заглушки. Наличие файла не означает его подключение к приложению.
- В v130.16 core/storage.js содержит реальный адаптер, но ещё не подключён к pos.html. sync/sync-manager.js описывает manual-only контракт, а не завершённую синхронизацию. Старые js/storage.js и js/sync.js — подготовительные слои, не замена текущему runtime.

## Обязательные архитектурные правила

1. iPad POS является SOURCE OF TRUTH. Авторитетные операционные данные находятся локально на iPad; backend и web — вторичные представления.
2. Архитектура OFFLINE-FIRST. Продажи, чеки, печать, смены, товары, локальные настройки и основные функции POS должны работать без интернета.
3. Локальные данные должны сохраняться до любых сетевых операций. Сохранение отделено от синхронизации; успешная локальная запись не зависит от доступности backend.
4. Основное направление данных: POS → Backend → Web / Mini App.
5. Backend не должен автоматически перезаписывать авторитетные локальные данные POS. Обычная синхронизация не заменяет локальное состояние удалённым. Будущий импорт backend → POS требует отдельного явного действия пользователя и отдельно согласованного поведения.
6. Синхронизация разрешена ТОЛЬКО вручную существующей кнопкой: Настройки → Сетевые настройки → Синхронизировать. В текущем pos.html её подпись — «Синхронизировать меню», обработчик — syncMenuToBackend(). Не создавать альтернативные триггеры.
7. Запрещена автоматическая синхронизация после изменения данных, по таймеру, при запуске приложения, при восстановлении интернета, в фоне и по network events. Запись в хранилище не должна запускать сеть. Учёт ожидающих изменений допустим без автоматической отправки; повтор синхронизации также инициирует пользователь.
8. Ошибка сети или backend никогда не должна блокировать локальную работу POS, отменять локальные операции, удалять или откатывать авторитетные данные.
9. Не менять существующий формат локальных данных без явной миграции и проверки совместимости. Сохранять логические ключи, префикс localStorage `prilavok_`, формы JSON, совместимость резервных копий, поддержку window.storage там, где он доступен, и локальное хранение на iPad без сети.
10. Миграцию хранения вести через локальный адаптер до подключения синхронизации к тем же данным. Не подменять действующие loadKey/saveKey неподключёнными или несовместимыми модулями одним изменением.

## Безопасное развитие и проверка

11. Перед изменениями проверять git status, Git-историю по затрагиваемой области и существующую реализацию; не предполагать её устройство. Проверять зависимости между UI, бизнес-логикой, хранением, синхронизацией и печатью. Сохранять посторонние изменения пользователя.
12. Не делать большие рефакторинги одним изменением. Мигрировать архитектуру постепенно: сначала границы и адаптеры, затем по одному бизнес-домену. Не разделять pos.html целиком за один шаг.
13. После каждого существенного этапа приложение проверяется на физическом iPad. После структурной миграции такая проверка обязательна до следующего шага; сборка или симулятор её не заменяют. Если проверки не было, явно сообщить об этом.
14. Не ломать печать чеков, кассу, товары, смены и существующие данные. Приоритеты: стабильность кассы → корректное локальное хранение → безопасная синхронизация → новые функции.
15. Каждую новую функцию проверять в интерфейсе, бизнес-логике, локальном сохранении и отображении/печати/синхронизации. После переноса логики обязательны регрессионные проверки оплаты и печати, включая работу без интернета и сохранность после перезапуска.
16. При изменении заказа или доставки проверять UI, пересчёт суммы, сохранение, чек и движение денег в смене. Исправление отображения также требует проверки бизнес-логики.
17. Сохранять iPad touch-интерфейс: крупные элементы, скруглённые блоки, простую навигацию и минимум действий. Не менять дизайн основных экранов без согласования.
18. Для существенного изменения описывать задачу, изменённые файлы, риски и способ/результат проверки.

## Версия и Git

19. Текущая рабочая контрольная версия — v130.18; пользователь подтвердил проверку на физическом iPad сообщением «Да все работает коректно». Повышение версии выполняется в рамках отдельно поставленной задачи, не как побочный результат изучения или документирования проекта.
20. Версия приложения должна постоянно отображаться справа в заголовке Настройки → Быстрые настройки; слева остаётся «Быстрые настройки». Компактная вторичная подпись текущей версии (сейчас «Версия 130.18») — постоянный элемент диагностики, который нельзя удалять при изменениях UI.
21. При повышении версии проверять согласованность core/constants.js, MARKETING_VERSION, Info.plist и отображаемой версии. Сейчас build phase «Stamp POS Version» вставляет подпись в собранный pos.html из MARKETING_VERSION; исходный HTML сам её не содержит.
22. При повышении версии избегать ненужного изменения PrilavokPOS.xcodeproj/project.pbxproj: менять только действительно необходимые значения, не переформатировать проект и не затрагивать подпись, идентификаторы и build settings без необходимости.
23. Не делать commit/push без явного указания пользователя, если отдельно не договорились иначе.

## Наблюдения о реализации v130.16

Эти наблюдения не являются исключениями из правил и не дают разрешения на исправления вне задачи:

- loadAll() запускает startWebOrderEvents() с EventSource для входящих web-заказов; это существующая автоматическая сетевая активность, а не доказательство выполнения manual-only контракта.
- saveProduct() при добавлении фото выполняет загрузку на backend перед saveKey('products', ...); этот путь ещё не соответствует правилу local-first.
- Требования архитектуры и фактическое состояние кода нужно различать. Устранять расхождения только постепенно в рамках согласованной задачи, сохраняя рабочую контрольную версию и проверяя результат на iPad.
