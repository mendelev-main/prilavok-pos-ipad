# Prilavok POS — процедура разработки

Постоянное руководство для работы с проектом в текущем чате Codex. Codex самостоятельно изучает репозиторий, проверяет изменения и сообщает результаты; ручная передача git diff в другой чат не требуется. Руководство не разрешает начинать новую версию или менять архитектурные требования вне задачи пользователя.

## 2. Главный архитектурный принцип

Единственный авторитетный SOURCE OF TRUTH для операционных данных — iPad POS.

```text
iPad POS
   ↓
локальное сохранение
   ↓
ручная синхронизация
   ↓
Backend
   ↓
Web / Mini App
```

Backend и web представляют данные POS. Не превращать Backend в обязательную зависимость локальной работы POS.

## 3. Offline-first

Без интернета должны работать запуск POS, загрузка локальных данных, товары, корзина, продажи, чеки, смены, остатки, локальные настройки и печать, если используемый принтер не требует интернета. Доступ к Bluetooth или локальной сети принтера не равнозначен доступу к интернету.

Сначала local commit — успешное локальное сохранение данных, не Git commit, — потом потенциальная сеть. Сетевая ошибка не отменяет уже сохранённое локальное действие и не блокирует кассу. Проверять фактическое завершение записи, а не только вызов async-функции без await.

## 4. Синхронизация

Стандартная синхронизация ТОЛЬКО ручная. Единственный разрешённый trigger:

**Настройки → Сетевые настройки → Синхронизировать**.

В текущем runtime кнопка подписана «Синхронизировать меню», обработчик — syncMenuToBackend(). Стандартное направление: POS → Backend → Web / Mini App.

Запрещены sync после save, background sync, timer, sync on launch, sync on reconnect, online/network events и скрытая автоматическая очередь, самостоятельно отправляющая данные. Допускается локальное pending/dirty состояние, но отправка и повторная попытка разрешены только после явного нажатия пользователем кнопки синхронизации.

Backend не должен молча перезаписывать более новые локальные POS данные; авторитетные локальные данные вообще не заменяются удалёнными при стандартной синхронизации. Будущий импорт backend → POS — отдельное явное действие с отдельно согласованным поведением. Сохранение данных не должно иметь сетевых побочных эффектов.

## 5. Существующие данные и persistence

Без отдельной явной миграции и проверки совместимости нельзя менять localStorage keys, prefix `prilavok_`, JSON structures, IDs и semantics существующих полей. Обновление поверх предыдущей версии должно сохранять пользовательские данные. Никогда не очищать localStorage для решения проблемы разработки.

Перед изменением persistence logic определить текущий read/write path: вызывающий код → loadKey/saveKey → adapter → выбранное хранилище. Проверить ключи, сериализацию, fallback, обработку исключений, порядок записи и последующих действий, восстановление после перезапуска и совместимость резервной копии.

Для v130.17:

- loadKey(key, fallback) → PrilavokCore.Storage.get(key, fallback, markStorageBroken).
- saveKey(key, value) → PrilavokCore.Storage.set(key, value), ошибки перехватывает фасад.
- При наличии window.storage используются get(key, false) и set(key, JSON.stringify(value), false), без префикса.
- Иначе используется localStorage с ключом `prilavok_` + key и теми же JSON.parse/JSON.stringify.
- Выбор провайдера фиксируется при загрузке через `typeof window.storage !== 'undefined'`. Значение null сохраняет legacy-поведение: ошибка и предупреждение, а не скрытое переключение провайдера.
- Ошибка чтения возвращает fallback и вызывает markStorageBroken; ошибка записи вызывает markStorageBroken и не выходит в вызывающий код.
- loadAll, его существующие нормализации и testLocalStorage не менялись. Диагностическая проверка удаляет только свой тестовый ключ; это не разрешение очищать пользовательские данные.

Fallback означает обработанную ошибку, а не успешное чтение. Не обещать восстановление повреждённых записей или гарантированное сохранение при недоступном хранилище. Испытания повреждённого JSON и отказов storage проводить только на искусственных данных.

## 6. Постепенная архитектурная миграция

pos.html остаётся большим монолитным legacy runtime. Не переписывать его целиком и не переносить несколько бизнес-доменов одним этапом.

```text
existing behavior → compatible adapter → test
                 → next small extraction → test
```

Один business domain за этап. Не смешивать архитектурный рефакторинг с визуальным редизайном или несвязанным исправлением. Проверять зависимости UI, бизнес-логики, локального хранения, синхронизации и печати. После существенной миграции — физический iPad до следующего этапа.

## 7. Git workflow и самостоятельный review

Перед каждой задачей из корня репозитория:

```sh
git status
git log --oneline -n 10
```

Зафиксировать исходное состояние. Не уничтожать неизвестные локальные изменения. Если файл изменён пользователем или Xcode, сначала изучить его diff и учитывать его при работе. Не использовать автоматически `git reset --hard`, `git clean -fd` или force push.

Не делать commit/push без явного разрешения пользователя, если он отдельно не изменил это правило. Разрешение на реализацию и успешный iPad test сами по себе не разрешают commit/push.

После реализации:

```sh
git diff --check
git status
git diff
```

Просмотреть также новые untracked-файлы: обычный git diff их не показывает. Для нового текстового файла можно использовать `git diff --no-index -- /dev/null path/to/file`; код 1 означает наличие различий. Не добавлять файл в индекс только ради просмотра diff.

Codex сам анализирует diff: проверяет границы задачи, случайные изменения, совместимость, ошибки и риски. Не просить пользователя копировать diff в другой чат, если он доступен здесь. Выполнить релевантные syntax/static checks, указать команды и результат; при невозможности проверки описать конкретную причину.

Для JavaScript проверить как внешние модули, так и inline script из pos.html; например, извлечь inline script во временный файл и выполнить `node --check`. Для persistence сравнить старый и новый путь на одинаковых тестовых данных, включая отсутствие ключа, null, повреждённый JSON, ошибки чтения/записи и запуск loadAll. Проверка синтаксиса не доказывает совместимость поведения.

## 8. Xcode project.pbxproj и ресурсы

Xcode может автоматически менять project.pbxproj. В истории 80430a6 уже сохранены DEVELOPMENT_TEAM и нормализация Debug/Release configuration entries. Не считать любое изменение проекта ошибкой.

Перед изменением определить необходимость, изучить исходный diff и минимизировать правки. Не удалять DEVELOPMENT_TEAM пользователя, не менять signing и bundle identifier без необходимости, не переформатировать файл целиком.

После изменения:

```sh
plutil -lint PrilavokPOS.xcodeproj/project.pbxproj
```

Проверить также ссылки между PBXFileReference, PBXBuildFile, группой, build phase и target. Корректный plist сам по себе не доказывает правильную упаковку ресурсов.

При добавлении Web или другого bundle resource проверить, нужен ли он runtime, как сохраняются пути и какие файлы реально исполняются. Для текущего подключения ожидается:

```text
PrilavokPOS.app/
  pos.html
  Web/js/core/storage.js
```

Проверять собранный bundle: наличие файла, совпадение его содержимого с исходным адаптером и порядок загрузки. Swift загружает pos.html через loadFileURL с allowingReadAccessTo родительской директории; локальный Web находится внутри этой области. Включение папки в Resources не исполняет все её скрипты автоматически.

## 9. Версии и VERSIONING-001

Текущая последовательность:

- v130.16 — предыдущая подтверждённая контрольная версия по указанию пользователя.
- v130.18 — текущая подтверждённая контрольная версия. Пользователь подтвердил physical iPad test: «Да все работает коректно».
- v130.17 — предыдущая подтверждённая контрольная версия. Пользователь после запуска и предложенного checklist сообщил: «Все работает».

Версия постоянно видна справа в header «Настройки → Быстрые настройки». Каждая тестируемая версия должна иметь однозначный видимый номер. Сейчас MARKETING_VERSION используется в Info.plist и Xcode build phase «Stamp POS Version», которая добавляет подпись в собранный pos.html. core/constants.js также содержит appVersion; проверять согласованность значений, не считать неподключённый constants.js источником подписи runtime.

**VERSIONING-001 — открытый технический долг.** Спроектировать более безопасный single source of truth для версии, чтобы обычное повышение версии по возможности не требовало изменения project.pbxproj и не конфликтовало с локальными изменениями Xcode. Решение должно согласовать bundle metadata и видимый номер в Debug/Release. Не менять рабочий механизм в рамках несвязанной задачи; нужен отдельный безопасный этап.

## 10. Physical iPad gate

Статические проверки не заменяют физический iPad. После существенного изменения пользователь собирает приложение в Xcode и проверяет его на физическом iPad. До его подтверждения версия не считается полностью validated. Codex не утверждает, что physical iPad test пройден, если пользователь его не выполнил и не подтвердил результат.

Минимальный regression checklist выбирается по области изменения; для общей миграции хранения проверять:

1. Сохранить резервную копию и зафиксировать исходные данные контрольной версии. Установить новую версию поверх приложения без удаления, с прежним bundle identifier.
2. Проверить запуск и видимый номер справа в «Быстрых настройках».
3. Проверить старые товары, цены, остатки, чеки, смены, настройки и отложенные заказы.
4. Проверить восстановление текущей корзины и данных после полного закрытия и перезапуска приложения.
5. Проверить изменение товара, сохранение и повторный запуск. В v130.17 базовый тест проводить без нового фото; image upload — отдельный известный риск.
6. Проверить корзину, количество, скидки и доставку, если используются.
7. Проверить продажи за наличные, картой и смешанную оплату, если используется; суммы чека и движение остатков.
8. Проверить новый чек и повторную печать старого чека доступным принтером.
9. Проверить открытие/закрытие смены, внесение/изъятие и итог кассы.
10. Повторить основные локальные сценарии без интернета; для печати сохранить необходимый Bluetooth или локальную сеть.
11. Проверить ручную синхронизацию существующей кнопкой в рамках разрешённого теста: успех при доступном backend и ошибку без интернета. Ошибка не отменяет локальные данные и не блокирует POS.

Результат фиксировать с версией, выполненными пунктами, обнаруженными проблемами и явным подтверждением пользователя. Если тест выявил ошибку — остаться на текущем этапе.

## 11. Definition of Done

Задача готова к iPad test только если требования выполнены, архитектурные правила не нарушены, diff просмотрен, нет случайных изменений, git diff --check проходит, доступные syntax/static checks проходят, совместимость данных рассмотрена, риски перечислены и дан короткий checklist для iPad.

Отдельно сообщать результат сборки. Если сборка заблокирована средой, не выдавать это за успешную сборку; можно передать пользователю исходники для сборки в его Xcode с точным описанием ограничения.

После успешного iPad test пользователь может разрешить commit/push. Не повышать статус версии до validated по результату статического анализа или наличию частично собранного bundle.

При review проверять независимо от прежнего отчёта:

- Чтение существующих данных и запись через фасад совместимы с контрольной версией. Ошибка загрузки самого скрипта не должна быть принята за пустую пользовательскую базу: проверять предупреждение и упаковку ресурса.

Технический долг не является исключением из архитектурных правил и не даёт разрешения на несогласованное исправление. В частности, существующий loadAll может применять defaults/нормализации после ошибок чтения; не проверять повреждение данных на рабочей кассе.

## 14. Порядок дальнейшей работы

1. Inspect: прочитать правила, status, log и существующую реализацию/diff.
2. Plan minimal change: обозначить границы, совместимость, риски и проверку.
3. Implement: внести только необходимые изменения текущей задачи.
4. Self-review diff: самостоятельно проверить весь diff, включая новые файлы.
5. Run checks: выполнить релевантные проверки и отделить успех от ограничений среды.
6. Report risks: сообщить изменения, файлы, результаты, совместимость и оставшиеся риски.
7. Ask for physical iPad test: дать короткий точный checklist и дождаться подтверждения пользователя.
8. После подтверждения пользователя — commit/push, только если пользователь разрешил.
9. Только затем следующая версия по отдельному указанию пользователя; автоматически её не начинать.

## v130.21 — заказы поставщикам и приёмка по ТТН

Пользователь согласовал средневзвешенную себестоимость. Новый заказ хранит requestVersion=1,
в строках requestedQty/requestedUnit (упаковка, коробка или совместимая физическая
единица), stockUnit, packSize и expectedQty. qty сохраняет ожидаемое базовое количество,
либо 0 при неизвестном размере упаковки; expectedQty=null явно означает отсутствие
оценки. Эти числа не являются приходом на склад. Старые заказы без новых полей
читаются прежним способом. Текст и нативный PDF используют снимок заказанного количества.
Количество разных единиц больше не суммируется как штуки. PDF принимает quantityText,
для старого payload сохранён fallback. Кассовый printReceipt не изменён.

В карточке простого товара можно задать purchaseUnit и purchasePackSize (размер в
неизменной базовой единице); в конкретном заказе значения можно переопределить.
После создания себестоимость readonly; saveProduct дополнительно сохраняет текущую
себестоимость независимо от поля UI. Смена единицы отображения не меняет её базовое
значение. Новая себестоимость при приходе: (остаток × себестоимость + сумма ТТН) /
(остаток + фактический приход), без округления себестоимости до двух знаков.
Суммы документов отображаются с точностью валюты. Для отрицательного остатка в
расчёте стоимости старый объём принимается равным нулю. Товары без учёта остатков
не увеличивают остаток; их себестоимость берётся из принятой строки.

Приёмка — единый экран для заказа и закупки без заказа. Поля ТТН: supplierId,
invoiceNumber, invoiceDate; в строках invoiceQty/invoiceUnit/invoiceUnitPrice как
снимок документа, qty/unitCost/totalCost по-прежнему в базовых единицах. При изменении
цены пересчитывается сумма; при вводе суммы выводится цена. Сумма строки является
основанием расчёта себестоимости. Все строки проверяются до изменения склада.
Непоставленная позиция задаётся как 0/0. Можно добавить дополнительные строки.
Предварительное подтверждение показывает итоговый остаток и себестоимость; при
финальном подтверждении расчёт повторяется по актуальному остатку. Повторное
подтверждение уже принятого заказа не создаёт повторный приход.

Явное «Сохранить черновик и выйти» сохраняет receivingDraftV2 в заказе; для приёмки
без заказа используется новый локальный ключ receivingDraft (с префиксом prilavok_).
Это единственный новый ключ; новых сетевых вызовов/автосинхронизации нет. Старые
receivingDraft поддерживаются при открытии. Незавершённые черновики не входят в
резервную копию; подтверждённые ТТН входят в существующий exportBackup. Автосохранения
ввода нет. Сохранение черновика проверяет ошибку адаптера и не закрывает экран при
ошибке. Проводка сохраняет существующие products/purchaseOrders/receivings через
saveKey; это прежнее сохранение в несколько ключей, не новая ACID-транзакция.

Заказ закрывается по факту одной подтверждённой приёмки, в том числе с расхождением;
остаток заказа автоматически не переносится. При неизвестном весе упаковки нельзя
вычислить недовоз по весу; нулевая поставка отмечается как расхождение. Полностью
нулевую ТТН подтверждать нельзя — остаётся черновик. Исторические чеки, себестоимость
продаж, старые приёмки и stockConsumption не мигрируются.
