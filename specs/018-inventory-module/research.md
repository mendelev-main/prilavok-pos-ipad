# Research: модуль инвентаризации

## Решение 1: переносить полный непрерывный домен

**Decision**: Перенести функции от расчёта периода инвентаризации до рендера рабочего экрана одним
компонентом; backup и настройки компании оставить в `pos.html`.

**Rationale**: Этот блок имеет единую модель состояния и UI, а соседние функции принадлежат другим
доменам. Такая граница исключает второй функциональный срез.

**Alternatives considered**: Отдельно переносить вычисления и UI отклонено, потому что оставило бы
один домен одновременно в двух файлах и не дало бы ясной границы сопровождения.

## Решение 2: сохранить классический глобальный контракт

**Decision**: Подключить `inventory.js` обычным `<script>` до `loadAll()` и не переименовывать функции.

**Rationale**: `render()`, inline handlers и другие части POS вызывают существующие глобальные имена.
Смена API в этом же этапе увеличила бы риск без пользы для пользователя.

**Alternatives considered**: ES modules, namespace и dependency injection отложены до тех пор, пока
inline UI постепенно не будет заменён компонентными границами.

## Решение 3: не отделять critical journal

**Decision**: Оставить `commitCriticalStorage`, `storageSnapshot` и `criticalOperationBusy` в общем
runtime и использовать их без изменения.

**Rationale**: Журнал обслуживает оплату, смены, приёмку, backup и инвентаризацию. Его перенос относится
к отдельному инфраструктурному этапу.

## Решение 4: выполнять production-файл в тестах

**Decision**: Fixture загружает `inventory.js` после основного inline runtime и до вызовов тестов.

**Rationale**: Существующие сценарии уже проверяют отказ записи, атомарную фиксацию, завершение и
восстановление journal. Они должны проверять подключённый файл, а не копию логики.

## Решение 5: не менять persisted-модель

**Decision**: Сохранить `inventoryConfig`, `inventoryHistory`, `inventoryDraft` и типы journal
`inventory-fix`/`inventory-complete` без миграции.

**Rationale**: Архитектурный этап меняет расположение исходного кода, а не пользовательские данные.
