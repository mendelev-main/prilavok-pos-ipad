# Проверка надёжности M POS

Дата: 2026-10-01. Статус: план и первичный аудит выполнены; полная приёмка открыта.
Рабочая ветка main сохранена. Это аудит, не новая функция и не новая версия приложения.

## User stories

### US1 — Достоверная документация (P1)
Как владелец, хочу различать существующий код, планы, отменённые решения и результаты проверок.
Приёмка: есть единый индекс, ссылки на актуальные MASTER/DELTA/LOYALTY, архив помечен историческим,
у каждого результата указаны версия/границы доказательства. Spec Kit настроен на реальные принципы.

### US2 — Сохранность денег и данных (P1)
Как кассир, хочу знать риски потери чеков, остатков, смен и бонусов при сбоях.
Приёмка: автоматические проверки и диагностика на искусственных данных выполнены;
каждая подтверждённая проблема имеет сценарий, последствия и способ повторной проверки.
Наличие ошибок не блокирует завершение аудита, но блокирует заявление production-ready.

### US3 — Полная приёмка приложения (P2)
Как владелец, хочу последовательный план проверки всех функциональных разделов и интеграций.
Приёмка плана: каждый раздел имеет шаги, ожидаемый результат, метод и статус.
Приёмка приложения: физические сценарии пройдены на iPad; критические ошибки исправлены и перепроверены.

## Functional requirements

- FR-001: Разделить текущую реализацию, открытые задачи и архив; не потерять историю решений.
- FR-002: Проверить установленный GitHub Spec Kit и использовать spec → plan → tasks → analyze.
- FR-003: Зафиксировать baseline POS/backend, незакоммиченные изменения и ограничения проверки.
- FR-004: Проверить оплату, возвраты, local storage, восстановление и склад на частичные отказы.
- FR-005: Проверить web-заказы, привязку клиента, лояльность и сетевые повторы.
- FR-006: Покрыть планом печать, отчёты, права, импорт/backup, настройки, навигацию и запуск.
- FR-007: Разделять воспроизведённую ошибку, вывод из кода и ещё не проверенную гипотезу.
- FR-008: Сохранить runtime, схемы и production-данные; исправления отдельными этапами.

## Edge cases

Нет сети/принтера; quota/повреждённый JSON; сбой между записями; повторный тап/ACK;
закрытие приложения до ответа; параллельная трата подарков; возврат после смены рецептуры;
смена закрыта; отсутствующий товар; неполный backup; истёкшее подтверждение телефона.

## Success criteria

SC-001: Все FR связаны с задачами и разделами матрицы.
SC-002: Для запускаемых проверок сохранены результаты; нет неподтверждённых отметок PASS.
SC-003: Для найденных ошибок указан порядок исправления и критерий закрытия.
SC-004: Код приложения, форматы данных и версия не изменены этим аудитом.
