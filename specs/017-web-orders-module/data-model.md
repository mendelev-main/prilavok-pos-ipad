# Data model: модуль WEB-заказов

Этап не меняет схему данных. Ниже зафиксированы существующие сущности для проверки совместимости.

## WEB-событие (`webEvents`)

- Хранится массивом под существующим storage-ключом `webEvents`.
- Идентификатор: `id`; отображаемый номер: `external_id`.
- Содержит статус, время создания, сумму, доставку, комментарий, клиента и `order_items`.
- В рабочем списке остаются события со статусом `new`.

## Журнал принятия (`webOrderAcceptances`)

- Хранится объектом, индексированным по id WEB-заказа.
- Стадии: `prepared` → `local` → `confirmed`.
- Содержит авторитетный snapshot `parked` и `readyEstimate`.
- Повтор операции использует существующую запись и не создаёт второй parked-заказ.

## Parked-заказ (`parked`)

- Хранится в общем существующем массиве отложенных заказов.
- Связь с сайтом задаётся полями `source: "web"`, `webOrderId`, `webOrderStatus`.
- Сохраняет товары, итог, доставку, клиента, комментарий и состояние кухонной печати.

## Время готовности (`readyEstimate`)

- Поддерживает существующие значения из набора оценок и формат `at:HH:MM`.
- Записывается локально в журнал до сетевого подтверждения.

## Инварианты

1. Локальный parked-заказ сохраняется до ACK backend.
2. Один `webOrderId` соответствует не более чем одному parked-заказу.
3. Ошибка ACK оставляет локальный заказ и журнал для повтора.
4. Подтверждённое событие удаляется из `webEvents`, локальный чек не удаляется.
5. Префикс `prilavok_` применяется только существующим storage adapter.
6. Настройки личного уведомления добавляются в совместимую запись `telegram` полями `deviceChatId` и `notifyOnlineOrders`; для старых записей уведомление выключено.
7. Личное Telegram-уведомление запускается только после успешной записи нового события в `webEvents`.
