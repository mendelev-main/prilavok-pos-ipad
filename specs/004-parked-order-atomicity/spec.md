# Feature Specification: атомарные отложенные чеки

**Feature Branch**: `main`  
**Created**: 2026-10-01  
**Status**: Implementation complete; physical acceptance pending  
**Roadmap**: R1 Production acceptance 130.52  
**Finding**: A003-F01

## User Scenarios & Testing

### US1 — безопасно отложить чек (Priority: P0)

Чек появляется в `parked`, а текущая сессия очищается как одна восстанавливаемая операция. Если
операцию нельзя начать, корзина и текущая сессия остаются на месте и POS не сообщает об успехе.

### US2 — безопасно открыть отложенный чек (Priority: P0)

Текущая сессия получает все данные чека, а запись удаляется из `parked` как одна восстанавливаемая
операция. Ошибка до journal не меняет UI или данные.

## Requirements

- **FR-001**: Сохранить существующие ключи `prilavok_parked` и `prilavok_currentOrderSession` и их JSON-формат.
- **FR-002**: Использовать существующий `criticalStorageJournal` для park и resume.
- **FR-003**: Не изменять `state` и не показывать успех до успешного commit.
- **FR-004**: После частичной записи перезапуск обязан завершить оба ключа из journal.
- **FR-005**: Двойное действие во время commit не должно создать дубль.
- **FR-006**: Печать кухни разрешена только после подтверждённого локального commit.
- **FR-007**: Не менять оплату, формат чеков, сеть, UI и версию приложения.

## Success Criteria

- **SC-001**: Ошибка создания journal оставляет текущий чек без изменений.
- **SC-002**: Ошибка одной записи восстанавливается после `loadAll()` без дубля или потери.
- **SC-003**: Успешные park/resume сохраняют прежние поля заказа и тариф доставки.
- **SC-004**: Все существующие тесты проходят; runtime собирается для Simulator.
